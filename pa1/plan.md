## Final design and spec alignment

- PA1 is the standalone `pptoken` tool implementing translation phases 1–3: UTF-8/UCN handling, trigraph replacement, line splicing, raw-string spelling restoration, comments, preprocessing-token grammar, and contextual header names, emitting the assignment's token-event output. Its formatted stdout is the CLI's explicit tool boundary, not an internal representation passed between production compiler phases. `IPPTokenStream` receives callbacks; this path does not construct another owning token-event vector.
- Independently reconstructed flow: stdin bytes → decoded source code points → fused phase-1/phase-2 view retaining physical source offsets → token-context-aware raw-literal range recognition and source-spelling restoration → phase-3 scanner → `IPPTokenStream` callbacks → `DebugPPTokenStream` stdout. Batch mode uses the same decode/translate/scan flow on each record. Input, translated character storage and bounded restoration coordinates have explicit lifetimes; the physical source is read-only during translation. The additional passes are linear in source size plus emitted spelling; delimiter matching is bounded by the C++11 16-character delimiter limit.
- PA1 does not contain the parser/semantic graph, template instantiation, LowIR optimizer, backend, or ELF writer. The spec's declaration/template-to-ELF and optimization legality/profitability/invalidation trace therefore has no PA1 implementation surface and is not inferred from this CLI audit. Integration of this tokenizer into those later stages remains an unaudited handoff, not a waiver of the global architecture audit.

## Findings and changes

1. **Raw-string source restoration lacked preprocessing-token context.** The prior phase-1/2 pass could mistake a raw-looking substring in an ordinary string, identifier/pp-number, comment, or include header for a raw-string introducer, suppressing required trigraph/splice translations. The correction fuses trigraph mapping and splicing while retaining source offsets, then recognizes raw literals only at token boundaries; its context walk skips comments, ordinary literals and user-defined suffixes, identifiers, pp-numbers and include header names. It restores physical spelling for the raw literal and leaves other text translated. Regression `tests/350-raw-literal-token-context.t` covers ordinary-string, identifier-adjacent, Unicode-identifier-adjacent, comment, and actual raw-literal cases. The new expected output follows N3485 [lex.pptoken] 2.5p3 and [lex.phases] 2.2p3: token formation is contextual, while phase-1 trigraph replacement applies outside a raw literal.
2. **Final-LF behavior after a terminal splice needed a focused case.** `tests/350-phase2-spliced-final-newline.t` is the reduced physical input `end\\` followed by LF. N3485 [lex.phases] 2.2p2 requires an additional LF where the source ends in a backslash immediately followed by the final LF; phase 2 removes that pair, leaving `end` plus the additional LF. Its expected events are `identifier(end)`, `new-line`, `eof`. This proof uses the standard, not compiler agreement.
3. **Block-comment newlines were discarded in phase 3.** The scanner treated an entire multiline `/* ... */` comment as one whitespace run and skipped every LF inside it. N3485 [lex.phases] 2.2p3 explicitly says comments become one space and newline characters are retained. The minimal reducer `a/*\\nb*/b` therefore requires events `identifier(a)`, whitespace, `new-line`, `identifier(b)`, final `new-line`, `eof`; baseline A and the prior implementation omit the internal `new-line`, while the corrected implementation emits it. The phase-3 scanner now emits internal comment LFs and keeps the comment's single replacement whitespace. The demonstrated change corrects stale references in `100-extra-comments.ref` and `900-real-world.ref`; no comparison mode or test coverage was weakened. The regression is `350-phase2-block-comment-newlines.t`.
4. **Reference policy / ambiguous case:** the only changed existing references are the two outputs shown wrong by the cited N3485 rule and reduced case; new sidecars cover the three added regressions. The reference bundle revision is `c2f713cd70d06170632bfde3e75dd6fe1aa44d98` from `reference-binaries/manifest.tsv`. This proof does not rely on compiler agreement. A proposed terminal `??/` without a physical final LF case was excluded because CWG 1698 records ambiguity in the ordering/intent; no expected result or reference correction is claimed for it.

## Performance evidence and acceptance

- No PA1 numeric latency, memory, runtime or code-size budget is stated in `spec.md` or the assignment. The prior handoff's request to collect measurements is evidence collection, not a pass/fail gate. No unsupported performance gate is used. There is no speculative optimization/IR transformation in this stage, so optimization legality, invalidation, fallback and IR-growth budgets are not applicable. The implementation's phase work is linear; raw delimiter work is bounded. `pptoken` emits tokens rather than compiled programs, so generated-program runtime/size and template-heavy compiler benchmarks are not PA1-applicable. The applicable executable runtime (the tokenizer itself), its peak RSS/text size, and compiler-object build cost were measured.
- Exploratory run with large A/A drift is retained but rejected for performance claims in `$RALPH_ARTIFACT_DIR/pa1-final-audit/`. The accepted comparison froze baseline A and candidate B binaries, C++11 `-O3` build settings and a 4,233,216-byte repeated real-world PA1 source input. Full source/binary/input hashes, both complete outputs and raw observations are retained under `$RALPH_ARTIFACT_DIR/pa1-final-audit-current/` (`frozen.sha256`, `correctness.json`, `observations.json`).
- Output equivalence: both binaries produced 24,305,668 bytes with identical SHA-256. A/A calibration used 10 paired repetitions; first/second wall-time ratios ranged 0.9714–1.0209 (median 0.9938), with an overall max/min wall-time ratio of 1.0374. Eight ABBA blocks used two observations per arm per block. Candidate/base median wall-time ratios by block ranged 0.3617–0.3748 (median 0.3653), a repeatable ~63.5% lower tokenizer wall time on this measured workload, well beyond A/A noise. Across ABBA observations, median peak RSS rose from 93,958 KiB to 99,464 KiB (+5.9%).
- Disclosed costs: one unpaired standalone object build was 3.03 s / 149,024 KiB baseline versus 3.51 s / 156,732 KiB candidate (indicative, not an ABBA build-time claim). Candidate ELF `.text` is 64,486 bytes versus 57,062 (+13.0%); total ELF file length is 119,024 versus 114,520 (+3.9%); summed section sizes are 93,420 versus 85,877 (+8.8%). There is no PA1 budget against which to turn these into gates. The measured tokenizer runtime benefit is repeatable and the memory, compile-time and code-size regressions are disclosed; this is not evidence about other inputs or later stages.
