## Independently reconstructed design and data flow

1. **CLI/source:** ordinary mode reads stdin bytes into one owned `std::string`; batch mode reads each harness input file into one owned `std::string`. The same source then goes to the shared phase-1–3 scanner. PA3's text protocol is a standalone assignment boundary, not an internal compiler transport.
2. **Translation/tokenization (inherited PA1):** `ScanPreprocessingTokens` currently decodes UTF-8 to a code-point vector; the shared tokenizer forms a phase-1/2 view and source-offset maps, finds/restores raw-literal ranges, creates a translated code-point vector, then scans it and calls `IPPTokenStream`. It handles logical newlines, comments, literal/token context, and reports phase errors to the CLI. Scanner callback spellings are copied into PA3's current-line token vector. Whitespace is discarded; line callbacks close and evaluate a nonempty logical line; EOF closes a final unterminated logical line and the CLI prints `eof`.
3. **Expression ownership/evaluation:** each logical line's `PA3Token` vector owns token spellings only until evaluation. The precedence parser consumes the vector once, rejects trailing/invalid grammar, converts integer and character spellings to course-defined 64-bit signed/unsigned values, applies arithmetic conversions, and formats one result. `defined` uses the assignment's mock first-UTF-8-code-unit rule. Short-circuit logical and conditional parsing consumes both branches for syntax/type facts but suppresses runtime-only faults in unselected operands; the conditional result type remains the common type. A catch boundary converts expression failures to one `error` line and clears tokens before the next logical line. Phase 1–3 failures instead fail the process as required.
4. **Representative end-to-end paths reviewed:** a spliced/comment-containing source line is normalized and split by the shared scanner before its tokens reach the Pratt parser; `defined alpha ? 10u : 1/0` evaluates `defined`, parses both arms and preserves the unsigned result type while not dividing by zero; `(1u << 63) / -1` applies unsigned conversions and avoids signed-overflow UB; `u'\\u00aa' + 2` passes scanner spelling into character decoding, UTF-16-range validation and unsigned arithmetic; invalid syntax and invalid character/literal tokens produce an isolated `error` without losing later lines. The committed focused PA3 input also covers alternate operators, boundary literals, malformed Unicode scalars and signed right shifts.

## Findings and changes

1. **Avoidable source-byte copy at the PA3 CLI boundary (fixed).** Both ordinary and batch mode previously streamed the input buffer through `std::ostringstream`, then called `source.str()` to make another owning string for the scanner. Replaced that staging with a 64 KiB buffered read loop appending directly into one `std::string`, then passed it by reference to the scanner. The owned source lifetime still covers the synchronous scan; semantics and error boundaries do not change. This does not make the inherited scanner streaming and does not claim to remove its translated code-point views.
2. **PA3 semantic review:** checked integer candidate selection against C++11 [lex.icon] as modified by the assignment's phase-7 type/promotion contract; character escape/scalar and prefixed-literal checks against the PA2/PA3 course contracts and C++11 [lex.ccon]; grammar, unary/binary precedence, usual signed/unsigned conversion, conditional result typing, division/remainder zero and shift-range behavior against the PA3 handout. No defect justifying a reference correction was found. Thus there is no reducer/reference change or bundle revision to report.
3. **No optimizer is introduced here.** The parser has bounded token consumption and constant work per operator apart from literal conversion. There are no IR transformations, optimization facts, invalidation chains, or IR growth in PA3; optimization legality/profitability/fallback and pipeline growth budgets are not applicable to this evaluator. Generated executable runtime/text benchmarks are likewise inapplicable because ppexpr does not compile programs.

## Performance evidence and stage-scoped acceptance

- No numeric latency, RSS, ppexpr runtime, or executable-size threshold is stated by the assignment/spec for this stage. The inherited PA3 request for measurements is an evidence request, not a performance pass/fail gate. The earlier plan's 492,075-line measurement is preserved as descriptive only; it was not treated as an optimization acceptance criterion.
- To evaluate the ownership cleanup, froze pre-cleanup A and final buffered-read C binaries, the same `-std=gnu++11 -Wall -O3` flags/input, and expected output under `$RALPH_ARTIFACT_DIR/pa3-final-audit/`. The input is 9,675,000 bytes / 600,000 expressions, formed by repeating eight expression paths (precedence, `defined`, conditional typing/lazy division, unsigned shift/division, logical short circuit, prefixed Unicode character, integer comparison and signed right shift). Every run's complete output was compared byte-for-byte with the fixed expected output; output SHA-256 was identical (`247c26fac43144ec04cc287651c03278c598caad3954ac928e9d88cfba7789d6`). Artifacts retain the frozen binaries and hashes, exact input and expected output, generator, build log/time, text-size reports, and each run's time/RSS/output hash.
- Final warmed serial A/A calibration (same hash for A and A2) was 2.23–2.51 s with RSS 180,360–180,540 KiB. Four balanced ABBA blocks show considerable later system drift: across four comparison blocks wall observations ranged 2.05–7.08 s, while peak RSS remained separated (A 179,804–180,428 KiB; C 170,796–170,972 KiB). Thus **no runtime improvement is claimed**; time spread overwhelms the possible effect. The candidate consistently reduced peak RSS by 9,340 KiB (about 9.1 MiB) on this 9.2 MiB input, consistent with eliminating a whole-source `ostringstream`/`.str()` staging copy. This is a source-ownership memory reduction, not an IR or generated-program claim.
- Frozen text size: A `.text` 112,743 bytes; C `.text` 110,888 bytes (1,855 bytes lower), no code growth. One forced C rebuild was 8.22 s / 146,108 KiB peak RSS; this single build measurement is descriptive, not an accepted compiler-latency A/B claim. Rebuilding the final binary twice produced the same SHA-256 (`36338c1a8a45d50df512a704bf1e7cfad044f1bb65220b2732415e78cf19ebba`) and identical section sizes. No fixed compiler benchmark suite exists on PA3 surfaces, and no generated executable is emitted here; the spec's full compiler/executable benchmark audit is a later-stage handoff, not asserted complete.
- **Inherited-plan acceptance reclassification:** PA1's audited frozen benchmark supports a repeatable ~63.5% tokenizer runtime reduction (ABBA median candidate/base ratio 0.3653), but disclosed +5.9% peak RSS, +13.0% `.text`, and slower single object build (3.03 to 3.51 s). There is no numeric PA1 budget, so this is a measured stage-specific improvement with costs disclosed, not grounds for a made-up rejection threshold. PA2's direct-callback/string-run plan reports descriptive timing/RSS/text, but no frozen A/B improvement claim or numeric gate; its course tests and bounded retained-string-run behavior are its acceptance. For PA3 the CLI staging-copy memory reduction is applicable and evidenced above; generated-program metrics are inapplicable. No unsupported performance gate is retained from inherited plans.
- The remaining full-source/translated-view footprint is inherited in `dev/src/preprocess/pp_tokenizer.cpp`: `decode_utf8` materializes code points, `Phase12View` materializes translated characters and offsets, `translate` creates a further result, and `Scanner` owns that result. This conflicts with the spec's eventual streaming-token-cursor/source-range direction. A PA3-local duplicate scanner would violate shared phase ownership; the issue is recorded as an explicit unaudited PA1→PA3 integration handoff, not falsely marked fixed or waived for whole-compiler architecture signoff.
